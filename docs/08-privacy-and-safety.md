# 08 — Privacy & Emotional Safety

> เจ้าของข้อมูล: กฎการเข้าถึงข้อมูล การเปิดเผยคำตอบ ข้อจำกัดด้านความปลอดภัย และการจัดการเนื้อหาอ่อนไหว
> **หลัก Honest Technology (P7):** เอกสารนี้และ UI ต้องไม่กล่าวอ้างการป้องกันที่ไม่ได้ทำจริง

## 3. Access Rules Matrix (Play Together, เครื่องเดียว)

| หน้าจอ/ข้อมูล | ผู้เล่น A ที่ผ่าน PIN/Handoff | ผู้เล่น B |
|---|---|---|
| คำตอบ Self ของ A (ยังไม่ Reveal) | อ่าน/แก้ | ไม่แสดง (แม้ชื่อตัวเลือก) — แสดงได้เพียง "A ตอบแล้ว" |

## 4. ข้อจำกัดของ PIN และ Local Storage (ต้องแสดงใน S10 และตอนตั้ง PIN)

### 4.1 สิ่งที่ PIN ทำได้

- กันไม่ให้อีกคน **เปิดดูผ่านหน้าจอของเกม** โดยบังเอิญหรือแบบไม่ตั้งใจ
- ทำให้การส่งเครื่องให้กันมีขั้นตอนชัดเจน

### 4.2 สิ่งที่ PIN ทำไม่ได้

- **ไม่ได้เข้ารหัสคำตอบ** — ข้อมูลใน localStorage เป็นข้อความธรรมดา (plain JSON)
- คนที่รู้วิธีเปิด Developer Tools ของเบราว์เซอร์สามารถอ่านคำตอบทั้งหมดได้โดยไม่ต้องรู้ PIN
- PIN 4–6 หลักสามารถถูกเดาได้ ถ้ามีคนตั้งใจ แม้จะมีการหน่วงเวลาหลังใส่ผิด
- การส่งออกที่มีข้อมูลของผู้เล่นอื่นซึ่งยังไม่ Reveal ต้องผ่าน PIN ของทุกคนที่ตั้งไว้ ([07](07-data-architecture.md) §11.1) — แต่ข้อจำกัดเรื่อง Developer Tools ยังอยู่
- ตัวนับการใส่ผิดและเวลาล็อกเก็บใน localStorage จึงถูกรีเซ็ตผ่าน Developer Tools ได้ — lockout เป็นเพียงตัวหน่วง ไม่ใช่การป้องกัน
- ใครก็กด "ลืม PIN" ได้ ซึ่งจะลบคำตอบที่ยังไม่ Reveal ของเจ้าของ PIN — จึงป้องกันการแอบดู แต่ไม่ป้องกันการลบข้อมูลของอีกคน (ดู §4.4)

### 4.3 ข้อความที่ต้องแสดงตอนตั้ง PIN (คำต่อคำ)

> PIN ช่วยกันไม่ให้อีกคนเปิดดูคำตอบของคุณผ่านหน้าจอเกม แต่ **ไม่ได้เข้ารหัสข้อมูล** คนที่มีความรู้ทางเทคนิคยังอ่านข้อมูลในเบราว์เซอร์นี้ได้ ถ้ามีเรื่องที่ไม่อยากให้ใครเห็นเลย อย่าเขียนลงในเครื่องที่ใช้ร่วมกัน หรือเลือก "ไม่สะดวกตอบ"

### 4.4 การทำงานของ PIN

- PBKDF2-SHA256, 210,000 iterations, salt 16 bytes ต่อผู้เล่น (WebCrypto) — เพื่อไม่ให้ PIN อยู่ในรูปข้อความเปล่า ไม่ใช่เพื่อเข้ารหัสข้อมูล
- ใส่ผิด 5 ครั้ง → ล็อก 30 วินาที, ครั้งที่ 10 → 5 นาที
- **ลืม PIN:** ลบ PIN ได้ แต่ต้องยืนยันว่าจะลบ "คำตอบที่ยังไม่ได้เปิดของผู้เล่นคนนั้น" ทั้งหมด (Self ที่ยังไม่ Reveal, Perceived ที่ยังไม่ Reveal, Reflection, Statements, Drafts) — เพื่อไม่ให้ "ลืม PIN" กลายเป็นทางลัดสำหรับอีกคน · หน้ายืนยันแสดงชื่อเจ้าของข้อมูลตัวใหญ่ และยืนยัน 2 ขั้น (กดปุ่ม + พิมพ์ชื่อเล่นของเจ้าของ PIN) เพื่อลดการกดผิดคน

### 4.5 ไฟล์ที่ส่งออก

- ไฟล์ JSON/TXT/PNG เป็นข้อความหรือภาพธรรมดา ไม่เข้ารหัส ใครได้ไฟล์ก็อ่านได้
- Checksum ในไฟล์ JSON ตรวจได้แค่ความเสียหาย **ไม่ได้กันการแก้ไข** ([07](07-data-architecture.md) §11.2)
- Import ไม่เชื่อสถานะ `revealed` จากไฟล์ที่มีหลายผู้เล่น ([07](07-data-architecture.md) §11.2 ข้อ 9)

### 4.6 การเข้ารหัส Local (ไม่อยู่ใน Scope ปัจจุบัน)

การเข้ารหัสข้อมูล Local ด้วย Passphrase (AES-GCM + PBKDF2) เป็นไปได้ทางเทคนิค แต่ **ไม่อยู่ใน MVP/Phase 2** เพราะ: ลืม Passphrase = ข้อมูลหายถาวร และเพิ่มความซับซ้อนมาก หากต้องการ ให้เพิ่มเป็นงานแยกพร้อมเอกสารฉบับนี้ (บันทึกเป็นแนวคิดใน [12](12-development-roadmap.md) Backlog)

## 5. Consent-based Reveal

กฎครบอยู่ใน [04](04-personality-system.md) §6.2 (R1–R7) เพิ่มเติมด้านความปลอดภัย:

- ปุ่มยินยอมต้องเป็นการกระทำโดยตั้งใจ (ปุ่มแยก ไม่มีการยินยอมอัตโนมัติ ไม่มีค่าเริ่มต้นเป็น "ยินยอม")
- "เปิดทีเดียวตอนจบบท" แสดงรายการข้อที่จะเปิดให้ตรวจก่อนยืนยัน และยกเลิกบางข้อได้
- ข้อความก่อนยืนยัน: *"เมื่อเปิดแล้ว {other} จะได้เห็นคำตอบนี้ และไม่สามารถทำให้ลืมได้"*
- ไม่มีการแจ้งเตือนกดดัน เช่น "{other} รอคุณอยู่นานแล้ว" — แสดงเพียงสถานะกลาง ๆ "{other} พร้อมแล้ว"

## 6. Remote Session Access Control

### 6.1 Phase 3A — Sealed Exchange (ไม่มี Backend)

**กลไก**
1. เมื่อส่งออก Sealed file: สร้างกุญแจสุ่ม AES-GCM 128-bit (`crypto.getRandomValues`) → เข้ารหัส JSON คำตอบ (เฉพาะ MirrorItem ที่เลือก) → ไฟล์มีเพียง `ciphertext`, `iv`, `questionIds`
2. กุญแจเก็บในเครื่องผู้ส่งเท่านั้น (`RemoteLink.myRevealKey`)
3. เมื่อยินยอม → แสดงกุญแจเป็น Base32 26 ตัวอักษร (แบ่งกลุ่มละ 4–5 ตัวให้อ่านง่าย) ให้ผู้เล่นส่งเอง
4. ผู้รับใส่กุญแจ → ถอดรหัส → ถ้า auth tag ไม่ผ่าน แสดง "รหัสไม่ถูกต้อง"

**ทำแล้ว (M12, 2026-11-23)** — `src/engine/sealed.ts`, `src/store/remote.ts`, S17 `/remote`
- ปิดผนึกเฉพาะคำตอบ Mirror ของตัวเอง (`self`) — คำเดาเกี่ยวกับคู่ (`perceived`) ไม่ออกจากเครื่อง
- ไฟล์ปิดผนึกมี `journeyId` เพิ่ม (ไม่ใช่คำตอบ) เพื่อจับคู่กับการเดินทางที่ถูกต้อง · นำเข้าไฟล์ของตัวเองถูกปฏิเสธ
- กุญแจสร้างครั้งเดียวต่อ journey และใช้ซ้ำกับไฟล์ใหม่ (IV ใหม่ทุกครั้ง)
- ขั้นตอนใน S17 อยู่หลัง PIN ของผู้เล่น · แสดงกุญแจต้องยืนยันก่อน
- 3B ออนไลน์แสดง "ออนไลน์: ยังไม่ได้ตั้งค่า" และกดไม่ได้

**สิ่งที่ระบบรับประกันได้**
- ผู้รับอ่านคำตอบไม่ได้ก่อนได้กุญแจ (ภายใต้สมมติฐานว่า AES-GCM ปลอดภัย และกุญแจไม่รั่ว)
- ผู้ส่งเปลี่ยนคำตอบหลังเห็นของอีกฝ่ายไม่ได้ โดยไม่ให้อีกฝ่ายรู้ (ไฟล์เดิมถูกส่งไปแล้ว)

**ข้อจำกัดที่ต้องแสดงใน S17 (คำต่อคำ)**
> • ระบบไม่สามารถบังคับให้อีกฝ่ายส่งรหัสเปิดกลับมาได้ — การเปิดพร้อมกันขึ้นอยู่กับความไว้ใจของทั้งคู่
> • รหัสที่ส่งไปแล้วเรียกคืนไม่ได้
> • ใครก็ตามที่ได้ทั้งไฟล์และรหัส จะอ่านคำตอบได้ ส่งผ่านช่องทางที่ไว้ใจ
> • ไม่มีการซิงก์อัตโนมัติ ต้องส่งไฟล์กันเอง

### 6.3 Phase 3C — Live (relay บนเซิร์ฟเวอร์ของเจ้าของ)

**กลไก**
1. เครื่องที่สร้างห้องสุ่ม **โค้ดห้อง** 10 ตัวอักษร (Crockford base32 = 50 bit, แสดงเป็น `XXXXX-XXXXX`) ด้วย `crypto.getRandomValues` แล้วคำนวณ `roomId` (128-bit) และกุญแจ AES-GCM 256-bit จากโค้ดในเบราว์เซอร์: PBKDF2-SHA-256, salt คงที่ `iywm-live-v1`, 300,000 รอบ, 384 bit (16 byte แรก = roomId, 32 byte หลัง = กุญแจ) — เซิร์ฟเวอร์ไม่เห็นโค้ด และการเดาโค้ดย้อนจาก `roomId` ต้องทำ PBKDF2 ราว 2^49 ครั้ง (ไม่คุ้มทำ)
2. เชิญได้สองทาง: **ลิงก์** `…/#/live?join=<roomId>.<key>` (กุญแจอยู่ใน fragment จึงไม่ถูกส่งไปเซิร์ฟเวอร์ใน HTTP request · หน้า S19 อ่านแล้วแทนที่ URL ด้วย `#/live` (replace)) หรือ **โค้ดห้อง** ที่อีกฝ่ายพิมพ์ใน S19 — โค้ดมีค่าเท่ากับลิงก์ ใครได้ไปก็อ่านได้ · พิมพ์ผิดตัว O/I/L ถูกแปลงเป็น 0/1 ให้
3. ทุกอย่างที่ส่งขึ้นเซิร์ฟเวอร์เข้ารหัสในเบราว์เซอร์ก่อน เซิร์ฟเวอร์เก็บแค่ `roomId`, ช่อง (0/1), ciphertext, เวลา — **อ่านชื่อ คำตอบ หรือเนื้อหาใด ๆ ไม่ได้**
4. แต่ละเครื่องเขียนได้เฉพาะช่องของตัวเอง (โทเค็นเขียนสุ่มต่อช่อง เก็บแค่ hash บนเซิร์ฟเวอร์)
5. ห้องไม่มีความเคลื่อนไหว 30 วัน → ลบอัตโนมัติ · ออกจากห้อง → ลบช่องของตัวเองทันที

**สิ่งที่ต่างจาก 3A — ต้องบอกผู้เล่นตรง ๆ ใน S19 (คำต่อคำ)**
> • เล่นสดเหมือนนั่งเล่นด้วยกันบนเครื่องเดียว: คำตอบส่วนตัวของแต่ละคนถูกส่ง (เข้ารหัส) ไปเก็บในเครื่องของอีกฝ่ายด้วย เกมจะไม่แสดงจนกว่าทั้งคู่ยินยอม แต่คนที่รู้วิธีเปิดข้อมูลเบราว์เซอร์ในเครื่องนั้นอ่านได้
> • เซิร์ฟเวอร์อ่านข้อมูลไม่ได้ แต่ใครได้ลิงก์เชิญเต็ม ๆ ก็อ่านได้ ส่งลิงก์ทางช่องทางที่ไว้ใจ และอย่าโพสต์ที่สาธารณะ
> • สิ่งที่อีกฝ่ายได้รับไปแล้วลบจากเครื่องเขาไม่ได้

PIN (ถ้าตั้ง) ยังป้องกันคนอื่นที่ใช้เครื่องเดียวกันตามเดิม · ข้อมูลที่ส่งเป็นชุดเดียวกับที่ Play Together มีในเครื่องเดียว (ผู้เล่นสองคน + โปรไฟล์ของเจ้าของช่อง + Journey) — ไม่ส่ง PIN, Drafts, Memories, Journey อื่น

### 6.2 Phase 3B — Supabase

**Identity:** Supabase Anonymous Sign-in ต่อเครื่อง (ไม่ขออีเมล) · ไม่มีการกู้บัญชีใน 3B แรก (แจ้งก่อนเริ่ม)

**Row Level Security (บังคับที่ฐานข้อมูล ไม่ใช่ที่ Client):**

| ตาราง | SELECT | INSERT/UPDATE | DELETE |
|---|---|---|---|
| `sessions` | สมาชิกของเซสชัน | INSERT: ผู้ใช้ที่ล็อกอิน (เป็น owner) · UPDATE: owner | owner |
| `invites` | ไม่มีใคร (ใช้ผ่าน RPC เท่านั้น) | RPC `create_invite` (owner) | RPC `revoke_invite` (owner) |
| `session_members` | สมาชิกของเซสชันเดียวกัน | RPC `join_session(code)` เท่านั้น | ตัวเอง (ออก) หรือ owner (ลบเซสชัน cascade) |
| `answers` | **เจ้าของแถวเท่านั้น** | เจ้าของแถว · ต้องเป็นสมาชิก | เจ้าของแถว |
| `consents` | สมาชิกของเซสชัน (เห็นว่าใครยินยอม ไม่เห็นคำตอบ) | เจ้าของแถว | เจ้าของแถว (ถอนยินยอม — เฉพาะก่อน revealed) |

**การอ่านคำตอบของอีกฝ่าย:** ผ่าน RPC `get_revealed(session_id, item_key)` (`SECURITY DEFINER` + `set search_path = public`) ที่คืนค่าเฉพาะเมื่อ:
1. ผู้เรียกเป็นสมาชิกของเซสชัน
2. ทั้งสองคนมีแถวใน `answers` สำหรับ `item_key`
3. ทั้งสองคนมีแถวใน `consents` ที่ `revision` ตรงกับ `answers.revision` ปัจจุบันของแต่ละคน
4. ฟิลด์ที่ผู้ตอบตั้ง `meta = prefer_not` ถูกแทนด้วย `{ "meta": "prefer_not" }`

**ทดสอบ RLS:** ต้องมี Integration test ที่พยายามอ่าน `answers` ของอีกคนโดยตรงแล้วต้องได้ 0 แถว (TC-RMT-05)

### 6.3 Invitation Code

- 8 ตัวอักษรจาก Crockford Base32 (ไม่มี I, L, O, U) ≈ 40 bits · แสดงเป็น `XXXX-XXXX`
- เก็บเป็น SHA-256 hash · หมดอายุ 7 วัน · ใช้ได้ครั้งเดียว (เผาเมื่อ B เข้าร่วม) · เซสชันรับสมาชิกได้สูงสุด 2 คน
- Rate limit การลองโค้ด: 10 ครั้ง/ชั่วโมง/ผู้ใช้ (Edge function หรือ Postgres function + ตาราง attempts)
- Rate limit การสร้างเซสชัน: 5 ครั้ง/วัน/ผู้ใช้ และมีเซสชันที่เปิดอยู่ได้พร้อมกันไม่เกิน 3 (กันการใช้ Anonymous sign-in สร้างสแปม)
- ลิงก์เชิญ (ถ้ามี) ใส่โค้ดใน fragment `#/remote?join=XXXX-XXXX` เท่านั้น — fragment ไม่ถูกส่งไป Server ใน HTTP request · หลังอ่านโค้ดแล้วแทนที่ URL ด้วย `#/remote` (replace) เพื่อไม่ให้โค้ดค้างใน history
- **ห้ามใส่คำตอบ ชื่อ หรือข้อมูลส่วนตัวใด ๆ ใน URL**

### 6.4 Revoke & Delete

| การกระทำ | ผู้ทำได้ | ผล |
|---|---|---|
| ยกเลิกโค้ดเชิญ | owner | `revoked_at` ตั้งค่า · โค้ดใช้ไม่ได้ทันที |
| ออกจากเซสชัน | member | ลบแถวของตัวเองใน `session_members`, `answers`, `consents` |
| ลบเซสชัน | owner | ลบ `sessions` (cascade ทุกตาราง) |
| หมดอายุ | ระบบ | ไม่มีกิจกรรม 90 วัน → ลบ (scheduled function) |

ข้อความที่ต้องแสดงตอนลบ: *"ข้อมูลบน Server จะถูกลบ แต่สิ่งที่อีกฝ่ายเปิดดูไปแล้วอาจยังอยู่ในเครื่องของเขา"*

## 7. Data Deletion (Local)

| การกระทำ | ที่อยู่ | ยืนยัน | ผล |
|---|---|---|---|
| ลบคำตอบข้อเดียว | S4 Edit | ไม่ต้อง (มี Undo 5 วินาที) | คืนเป็น "ยังไม่ตอบ" · ลบจริงเมื่อหมดเวลา Undo |
| ลบ Next Conversation item | S9 | ไม่ต้อง (Undo) | — |
| ลบ Journey | S1b, S10 | ConfirmDialog | ลบ Journey + StoryAnswers + MirrorItems ของ Journey นั้น · Player และ Profile ยังอยู่ |
| ลบผู้เล่น | S10 | ConfirmDialog + PIN ของผู้เล่นนั้น | ลบ Player + Profile ทั้งสองชั้น + คำตอบใน Journey ทุกอัน · Journey ที่เหลือผู้เล่นคนเดียวเปลี่ยนเป็น `archived` |
| ลบข้อมูลทั้งหมด | S10 | พิมพ์ "ลบทั้งหมด" | ลบ `iywm:save`, `iywm:save:backup`, `iywm:probe` · กลับ S1 |

ทุกการลบ: แจ้งตรง ๆ ว่า "ไฟล์ที่คุณเคยส่งออกไว้ จะไม่ถูกลบ" · การลบทำจริงทันที (ไม่มี soft delete ใน local) · ทุกการลบต้องลบ `iywm:save:backup` และ Drafts ที่เกี่ยวข้องด้วย ([07](07-data-architecture.md) §10) — ไม่อย่างนั้นข้อมูลที่ลบแล้วยังค้างอยู่ใน backup

## 9. Sensitive Content Handling

### 9.1 Content Notes

- S1a และ S5 แจ้ง: *"เรื่องนี้มีฉากติดอยู่ในที่แคบ ความกลัว และการทะเลาะกัน"*

### 9.2 เนื้อหาที่เกมไม่รวม

ความรุนแรงทางกาย, การทำร้ายตัวเอง, การนอกใจ, การเสียชีวิต, การบาดเจ็บสาหัส, การดูถูกตามอัตลักษณ์ — ฉากลิฟต์จบด้วยความปลอดภัยของทุกคนเสมอ

### 9.3 Local Keyword Support Card (A-21)

- เมื่อผู้เล่นบันทึกข้อความอิสระ ระบบตรวจ **ในเครื่อง** กับรายการคำสั้น ๆ (เช่น "อยากตาย", "ฆ่าตัวตาย", "ทำร้ายตัวเอง", "ตบ", "ทำร้ายร่างกาย", "ขู่ฆ่า", "ไม่ปลอดภัย")
- ถ้าพบ → แสดงการ์ดอ่อนโยนที่ปิดได้: *"ถ้าตอนนี้คุณหรือใครสักคนไม่ปลอดภัย คุณไม่จำเป็นต้องรับมือคนเดียว"* + รายการ §9.4
- **ไม่บันทึก** ว่าพบคำใด ไม่ส่งข้อมูลไปที่ใด ไม่บล็อกการบันทึก ไม่แจ้งผู้เล่นอีกคน
- แสดงไม่เกิน 1 ครั้งต่อการเปิดแอป
- รายการคำเป็นไฟล์ Content แยก แก้ไขได้ (`src/content/th/safety.ts` — `SUPPORT_KEYWORDS`) · ตรวจตอนบันทึกข้อความอิสระทุกจุด: S4, Reflection, Interpretation, Mirror, ประโยค Ch5, "พิมพ์เอง", Next Conversation

## 10. Web Security (Static Hosting)

- HTTPS เท่านั้น
- Content-Security-Policy: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'` (+ โดเมน Supabase ใน 3B) · ไม่มี third-party script
- ฟอนต์และ Asset self-host ทั้งหมด (ไม่เรียก Google Fonts ตอน runtime)
- ข้อความจากผู้ใช้ render เป็น text node เท่านั้น ห้าม `dangerouslySetInnerHTML`
- ไม่มี cookie

## 11. Legal (ถ้าเผยแพร่สาธารณะ — Q-03)

ถ้าเผยแพร่สาธารณะและใช้ Phase 3B (ข้อมูลอยู่บน Server) ต้องเพิ่มก่อนปล่อย: Privacy Policy ตาม พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล (PDPA) · ระบุผู้ควบคุมข้อมูล · ตำแหน่ง Server · ระยะเวลาเก็บ · ช่องทางขอลบข้อมูล — **ต้องให้ผู้รู้ด้านกฎหมายตรวจ** เอกสารนี้ไม่ใช่คำแนะนำทางกฎหมาย
